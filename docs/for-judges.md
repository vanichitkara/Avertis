# Avertis — how to try it

**Command centre:** <https://avertis.web.app>

Nothing to install to see that. The Android app is optional and adds the
offline half of the story.

Avertis is a disaster-response platform for when communication
infrastructure fails. Phones relay for each other over Bluetooth with no
network, reports become structured incidents, and — the part worth your
attention — **the recommended responder changes when the communication
network changes**, not just when the physical situation does.

---

## 1. The dashboard (2 minutes, nothing to install)

Open <https://avertis.web.app>.

**Check the badge, top right.** It names the reasoning engine in use. Green
with a Gemini model means Gemini is live; amber means it has fallen back to
deterministic rules. The system never presents rule output as model output,
so whatever it says is what produced everything below it.

Then look at:

- **Operational decision** — the recommended responder, how reachable they
  are over the mesh, how far away, and the hazard on the route.
- **WHY?** — the explanation, generated from the figures beside it. It is
  grounded in measured state; nothing is invented.
- **Network** — nodes, reachable count, partitions. The topology below is
  coloured by partition: when the mesh splits, no link crosses between
  colours.
- **Incidents** — note the "duplicate reports absorbed" line. Many people
  reporting one event arrive as one incident with several sources.
- **AI activity** — what the system did, in order.

## 2. The signature behaviour (3 minutes)

This is the claim the project rests on, and you can watch it happen.

Scroll to **AI activity** and look for this sequence:

```
RECOMMENDATION      resp-a …  (100% reliability, 200 m)
PARTITION DETECTED  network split into 3 partitions
RECOMMENDATION      resp-b …  (70% reliability, 300 m)
RESPONSE REPLANNED  INC-0001: resp-a → resp-b
PARTITION HEALED    network rejoined into 1 partition
RESPONSE REPLANNED  INC-0001: resp-b → resp-a
```

What happened: a relay node failed. **Nothing physical changed** — responder
A was closer before and is still closer. But A ended up in a different
network partition, unreachable from the incident site, so the
recommendation moved to B. When the relay recovered, it moved back.

A distance-only system would have dispatched A both times, to someone who
could not be contacted.

Worth knowing how that decision is made: **the responder choice is
deterministic, not generated by the model.** It is a weighted score over
reachability, distance and hazard. That is deliberate — the same state must
always give the same answer, a dispatch decision should be reconstructible
from numbers, and during a network partition the model may be exactly what
is unreachable. Gemini explains the decision and does the language work
(structuring reports, judging whether two reports describe one event, and
writing the WHY); it does not pick who gets rescued.

## 3. The Android app (5 minutes, one phone)

**Download:** `avertis-arm64.apk` (20 MB) — [upload to Drive and put the
link here]

For an older 32-bit phone, use `avertis-arm32.apk` (18 MB) instead.

Open the file on an Android phone and allow installation from unknown
sources when asked. It is signed with debug keys, as hackathon builds
normally are, so Android will warn about an unknown developer.

No account, no setup. It opens straight to a working SOS button.

### Try this, in order

1. **Home** — internet shown as offline, mesh searching, your node id. The
   app assumes no connectivity; that is the normal case it is built for.
2. **SOS** → choose how many people need help → send.
   With no other phone nearby it says: *"No nodes in range yet. It is saved
   on this device and will be sent automatically when one appears."* That
   is the honest answer, and the report is genuinely held on the device.
3. **Report incident** — type something, or record a voice note, or attach
   a photo. A voice-only report is labelled "not yet transcribed" rather
   than being given invented words.
4. **My reports** — force-quit the app and reopen. The reports are still
   there, still marked as awaiting acknowledgement.
5. **Situation view** (radar icon) — nearby nodes by real bearing and
   distance. Deliberately not a street map: map tiles need the network that
   has just failed.
6. **Mesh screen** (hub icon) — node state, packet counters, and the radio
   switch between the simulated radio and real Bluetooth.

### Connect it to the live command centre

On the mesh screen, press **SYNC NOW**. The report is sent to the deployed
backend, Gemini structures it, and it appears on the dashboard within a few
seconds — with the headcount you chose.

### With two phones

Switch both to **Bluetooth** on the mesh screen. They discover each other,
and an SOS sent on one appears in the other's mesh activity. With three, a
phone out of range of the first receives it via the second.

## 4. What is honest to say about this

- **Physical Bluetooth is the least proven part.** Both roles are
  implemented, including a Kotlin layer for advertising that Flutter does
  not provide, and the framing is unit-tested — but it has had little time
  on real handsets. If it does not come up on your phones, that is the
  reason.
- **The command centre is a simulated disaster-management centre.** There is
  no integration with any real emergency authority, and none is claimed.
- **Confidence is capped at 0.95** and derived from evidence actually
  present — how many independent sources, whether there is a location,
  whether a headcount was stated. No single report justifies certainty.
- **Severity can only ever be raised.** The sender's own priority, the rules
  and the model each get a say, and the most severe wins. Under-triage is
  the dangerous direction.
- **Every recommendation requires human approval** and carries safety flags
  (`SINGLE_SOURCE`, `RECOMMENDED_RESPONDER_UNREACHABLE`,
  `UNKNOWN_HEADCOUNT`). The system recommends; a person dispatches.
- The state you are looking at was produced by a simulator driving the real
  backend. It is not seeded or hand-written.

---

## 5. If something does not work

- **Dashboard slow on first load** — Cloud Run scales to zero; the first
  request wakes it and takes a few seconds.
- **Badge says "rules"** — Gemini is rate-limited. The system falls back
  deliberately rather than failing, and says so instead of pretending.
- **"backend unreachable"** — the service is down or you are offline; the
  dashboard says so rather than showing stale numbers as if live.
- **SYNC NOW fails** — the phone has no internet. The report is kept, not
  lost; try again when connected.
